# WinAudioBridge 测试方案

## 1. 文档目标

本文档用于明确 WinAudioBridge 当前阶段的测试策略，避免 Windows 端与 Android 端重复构造对端 Mock，降低测试维护成本，并保证协议与关键业务逻辑具备可持续回归能力。

## 2. 总体原则

本项目测试采用“**契约测试 + 本地纯逻辑单元测试 + 少量跨端集成测试**”的分层策略。

核心原则如下：

- 不对 Windows 端和 Android 端重复编写“互相 Mock 对端”的测试
- 协议样本由两端共享，保证协议语义一致
- 单元测试优先覆盖纯逻辑、纯数据转换、选择策略与配置归一化逻辑
- 真正依赖设备、ADB、Socket、音量会话、`AudioTrack` 的链路，仅保留少量集成/联调用例

## 3. 分层测试策略

### 3.1 协议契约测试

目标：验证协议结构和字段语义一致。

建议覆盖：

- `SessionInit`
- `AudioFrame`
- `Heartbeat`
- `AndroidPlaybackStatus`
- `AndroidPlaybackStatusAck`
- `VolumeCatalogSnapshot`
- `CommandAck`
- 非法协议头
- 非法 `PayloadLength`
- 未知消息类型

建议方式：

- 建立共享协议样本目录
- Windows 与 Android 分别对同一批样本进行解析和断言

### 3.2 Windows 端单元测试

目标：只验证 Windows 本地纯逻辑，不依赖 Android 端存在。

首批建议覆盖：

- `SettingsService` 配置归一化逻辑
- `StreamingCoordinator` 目标设备选择逻辑
- `VolumeIconService` 图标键/摘要逻辑

不建议在单元测试中直接覆盖：

- ADB 真连接
- WASAPI 真采集
- Core Audio 真音量控制
- 真实 TCP 连接

### 3.3 Android 端单元测试

目标：只验证 Android 本地解析、状态合并与 ViewModel 行为。

建议覆盖：

- 协议 JSON/二进制解析
- `PlaybackStateRepository` 对目录、回执、增量消息的合并逻辑
- icon 保留与覆盖逻辑

当前已落地：

- `WindowsVolumeJsonCodec` 请求构造与 JSON 解析测试
- `ProtocolReader` 二进制协议包解析测试
- `ProtocolReader` `Heartbeat` 保活包解析测试
- 非法协议头校验测试

### 3.4 少量跨端集成测试

目标：验证关键真实链路。

建议仅保留：

- 建链成功
- `SessionInit` 成功
- 音量目录拉取成功
- 主音量调整成功
- 应用音量调整成功
- 断线自动重连成功

## 4. 当前实施顺序

当前优先级如下：

1. 先补 Windows 端纯逻辑单元测试
2. 再补 Android 端协议/状态单元测试
3. 最后补少量真机联调清单

当前执行结果：

- Windows 首批纯逻辑单元测试已完成并通过
- Android 首批协议解析单元测试已完成并通过

## 5. 当前已落地的首批 Windows 测试范围

本轮测试先覆盖以下内容：

- `SettingsService.Normalize()`
- `StreamingCoordinator.SelectTargetDevice()`
- `VolumeIconService.CreateIconKey()` / `GetIconHash()`

这些测试具有以下特点：

- 无需 Android 端 Mock 服务
- 无需真实 ADB
- 无需真实 Socket
- 执行快、稳定、适合持续集成

## 6.1 锁屏空闲回归清单

针对“Android 锁屏且 Windows 长时间无音频后恢复无声”问题，新增以下真机 smoke test：

- Android 启动前台服务并建立连接后锁屏 2 到 5 分钟
- 锁屏期间 Windows 保持无系统音频输出
- 观察 Android 日志中持续出现 `HEARTBEAT` 或空闲存活日志
- 恢复 Windows 系统音频输出后，Android 无需重启服务即可继续出声
- 连续重复至少 3 次，覆盖短空闲与长空闲两种时长

## 6.2 Android 播放状态心跳与重启音频回归清单

针对“Windows 显示已连接但 Android 不播放或延迟持续累积”问题，新增以下回归项：

- Android 与 Windows 建立连接后，Android 日志应周期性出现播放状态上报，Windows 日志应出现播放状态接收与 ACK 回包摘要
- 手动关闭或杀掉 Android 接收端后，Windows 应在播放状态超时后将链路置为故障，并按自动重连设置发起重连
- 模拟 Android 连续上报未播放状态时，Windows 应在达到连续异常阈值后重建音频链路
- 右键 Windows 托盘图标点击“重启音频”，应停止当前采集和传输，然后重新建立 ADB forward、TCP 连接和音频采集
- 关闭自动重连后触发播放状态超时，Windows 应记录故障但不自动重连

当前自动化验证结果：

- Windows：`dotnet test .\WinAudioBridge.sln /p:UseAppHost=false`，56 项测试全部通过
- Android：`gradlew testDebugUnitTest`，通过

当前仍需真机验证：

- Android 接收端断开或被杀后，Windows 是否在播放状态超时后重连
- 托盘“重启音频”是否能在真实播放中恢复音频

## 6.3 统一服务器拓扑 / LAN 模式 / 延迟显示测试项

针对“support-local-network-streaming”变更（Windows 作服务器、Android 作客户端、LAN 发现与延迟测量），新增测试项：

### 单元测试（已落地）

- Windows：`AudioTransportService` 服务器监听、接受客户端、新客户端替换旧客户端、停止监听
- Windows：`AudioTransportService` 发送 `LatencyProbe`（8 字节毫秒时间戳）与 `LatencyProbeAck` 回显
- Windows：`StreamingCoordinator.IsLanMode` 模式判定
- Android：`ProtocolReader` 解析 `LatencyProbe` / `LatencyProbeAck`
- Android：`LanDiscoveryClient.parseAnnounce` 公告解析（有效 / 无效 / 缺字段 / 类型不匹配）
- Android：`AudioBridgeService.resolveConnectTarget` 连接目标回退（显式 LAN / 默认 USB reverse）

### 真机冒烟清单

- ADB 链路（USB）：Windows 监听 `0.0.0.0:5000`（双端口之一）+ `adb reverse` → Android 主动连接 → 推流 → 音量控制；设备拔插后 reverse 自动重建
- LAN 链路（Wi-Fi）：Android 发现列表出现 Windows → 连接 → 推流 → 音量控制 → 延迟显示（估算延迟随网络变化）
- **双端口接入**：Android 分别经 reverse（`127.0.0.1:5000`）、局域网发现（`6000`）、手动输入（`5000` 或 `6000`）三种方式均能接入同一 Windows
- 断线重连：断线后 Android 自动重连（重连循环异常不退出）；服务器新客户端接入时旧客户端被替换
- 手动回退：广播不可达（AP 隔离）时手动输入 IP 端口可连接
- **主页直达**：主页「重连」按钮直接重连保存的局域网服务器，无需进设置页；连接状态徽章随连接状态变化（已连接 / 连接中 / 未连接）
- **配置持久化**：手动连接保存后重启应用，详情页手动输入框自动预填，应用启动自动连接该服务器

## 7. 结论

本项目不建议让 Windows 与 Android 两端都重复构造对端 Mock。

推荐做法是：

- 协议一致性测一次
- 本地纯逻辑分别测一次
- 真链路少量测一次

该策略能在保证质量的同时，显著降低测试冗余与维护成本。
